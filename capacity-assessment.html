Raku's Kitchen — What It Can Handle Today

A grounded read of real-world traffic and transaction volume the app reliably serves as built, from the actual code and current architecture — not theoretical peak numbers.

Architecture Next 14 · Vercel serverless · Firestore (Spark) · Razorpay Baseline ~1,000 orders/month Assessed 2026-09-26
🟢 Handles it comfortably

At its ~1,000-orders/month target the app runs at single-digit-to-~12% of every service limit. The realistic ceiling before anything needs re-architecting is roughly 10,000–15,000 orders/month — a 10–15× runway. The limits that bite first are operational (manual refunds, admin read volume), not compute.

01 The architecture, as built

Confirmed from the repo — env keys, configs, and code paths. No assumptions about infrastructure that isn't there.

  • Frontend + API: Next.js 14 App Router. No vercel.json or Dockerfile; a plain next.config.mjs → standard Vercel serverless deploy, which autoscales horizontally.
  • Data: Firestore, Spark (free) tier signals — single database, empty firestore.indexes.json.
  • Payments: Razorpay (order + verify + webhook), server-side keys.
  • Auth: Firebase Auth (phone OTP), token-verified on every protected route.
  • Address: Ola Maps (autocomplete + reverse-geocode) via server proxy.
  • Delivery: Borzo (API) + Shadowfax (API) + Porter (manual clipboard/deep-link), admin-triggered.
  • Menu/cart: fully static + localStorage — zero backend cost.

02 The limiting component

Load is wildly uneven across flows. Browsing is free; order completion is the only path that touches shared, stateful services. Here is where each ceiling actually sits.

Browsing / cart ∞

Static assets + localStorage. Thousands of concurrent visitors cost the backend nothing. Never the limit.

Firestore writes ~5% used

~12 writes/order. A 100-order peak day ≈ 1,200 / 20,000 daily Spark quota.

Firestore reads ~10–12%

Admin dashboard uses a live onSnapshot listener — incremental, not a re-read per view. Still the largest read consumer; watch it as order count grows.

Razorpay ~2 calls/order

orders.create + payments.fetch. Webhooks cost zero API calls (local HMAC). Trivial at this volume.

Ola Maps ~7% used

Autocomplete + reverse-geocode only. ~6 calls per address; the abort signal now propagates server-side, so cancelled keystrokes no longer bill. First external tier to fill, but only near ~10k orders/mo.

meta/counters hotspot

One shared doc read+written on every order to mint RK-#####. Not a hard limit — a contention point if sustained order rate ever gets high. Fine at 1,000/mo.

04 Ola Maps — the first external tier to fill

Only two Ola products are used: Autocomplete and Reverse Geocode. Address entry — not orders — is the billing unit, and abandoned checkouts still cost the autocomplete calls made while typing. ~5 autocomplete + ~1 reverse-geo ≈ 6 calls/address; with abandonment, ~9 calls per order-equivalent. Autocomplete (the ~5×-per-address product) hits its 100k free wall first, around 10,000–13,000 orders/month; reverse-geocode has vast headroom. On per-minute burst: ~500 people entering addresses in the same minute could brush the ~500 req/min autocomplete rate limit and see HTTP 429 — a promo-spike concern, not a daily one. The recent fix propagating the browser's abort signal server-side means cancelled keystrokes no longer bill, which stretches this headroom further.

Quota capacity ~13k orders/mo · per-minute burst capacity ~a few hundred concurrent typers before 429 · production-safe ~7–8k orders/mo with headroom under both.

Cost: ₹0 through ~10k orders/mo (inside free tier). Beyond, cost = (autocomplete − 100k) × Ola's per-call overage rate — confirm that rate in your dashboard; the figure isn't publicly verifiable here.

05 What actually breaks first

At this scale the real risks are operational, not capacity. These bite before any compute limit does.

No automated refund path

Payment is collected upfront, but cancelling a paid order only sets status Cancelled + sends a WhatsApp note — no money is returned programmatically. Every cancelled paid order needs a manual refund in the Razorpay dashboard. At 1,000 orders/month with any cancellation rate, this is a recurring manual burden and a customer-trust risk.

Admin dashboard read volume scales with order count

The live listener is efficient, but a growing orders collection means each dashboard attach reads more docs. Toward ~10k orders/month, watch the 50k/day read quota — the fix is archiving/paginating old orders, not re-architecting.

Ola Maps calls aren't cancelled server-side

Cancelled autocomplete requests still cost an Ola API call. A cost/quota consideration under heavy concurrent address entry; one-line fix is to propagate the request's abort signal into the route.

06 The honest ceiling

Today, reliably: the app comfortably serves its 1,000-orders/month target with a 10–15× headroom before any service limit forces a change. Thousands can browse concurrently at no backend cost; dozens can check out in the same minute without trouble.

First thing to change if you grow ~10×: archive old orders (protects the admin read quota) and, only if sustained order rate climbs, replace the single meta/counters doc with a sharded counter or Firestore auto-id. Neither is needed now.
