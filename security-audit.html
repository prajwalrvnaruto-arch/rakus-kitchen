02 Findings

Ranked by realistic impact. Each names the code path that proves it, and its resolution.

CriticalUnauthenticated, unthrottled Ola proxy routes

Both maps/* routes had no auth and no rate limit, and each proxies a billable Ola call. The client debounce lives in AddressPicker.tsx — UI, not a boundary. An attacker looping curl at 100 req/s burns ~360k Ola calls/hour: the monthly free tier gone in ~15 minutes, then paid overage or a 429 that breaks address entry for real customers. One anonymous machine, no login.

FixedBoth routes now require a signed-in user (requireUser), enforce a UID+IP sliding-window limit (40/min), and serve identical recent queries from a 60s cache. The abort signal also now propagates server-side, so cancelled keystrokes stop billing.
HighRate-limit identifier is UID-only on checkout

create-order's limit is keyed by Firebase UID. Phone-OTP signup lets an attacker mint new UIDs, so the per-account cap multiplies with account count.

Mitigated / notedThe maps limiter now includes client IP. For checkout, a decision was made to defer edge/global rate limiting; the real fix is a CAPTCHA on OTP signup plus edge limiting, tracked as a later item.
MediumNo cache / body-size limit on maps input

Repeated identical queries re-billed, and the attacker-controlled q had no size bound.

Partly fixedShort-TTL cache added. A hard query-length cap is a small follow-up.
MediumNo refund path for cancelled paid orders

Payment is upfront; cancelling only sets status and sends a WhatsApp note — no money is returned programmatically. Not an abuse vector, but a real operational gap surfaced by the review.

03 The nine questions, answered

1. Can an anonymous attacker generate unlimited expensive requests?
No longer. The Ola routes — the only anonymous vector — now require sign-in.
2. Can a normal authenticated user generate unlimited expensive requests?
No. Checkout is 5/60s per UID; maps are 40/min per UID+IP.
3. Can someone bypass the UI and call expensive APIs directly?
They can reach the routes, but not unauthenticated or unthrottled. Auth + rate limits apply server-side regardless of the UI.
4. Can someone exhaust the Ola Maps quota?
No longer trivially. Was the critical finding; now auth-gated, rate-limited, and cached.
5. Can someone exhaust the Firestore Spark quota?
Only slowly, via account rotation. Bounded by per-UID limits and OTP friction. See the High finding.
6. Can someone create unlimited fake orders / payment attempts?
No unlimited. Bounded per UID; no completed payment means no real order. Idempotent finalize prevents duplicates.
7. Can someone cause unexpected third-party costs?
Largely closed. Ola (the main risk) is fixed; Razorpay order-create is bounded per UID.
8. Single biggest abuse vulnerability?
Was the unauthenticated Ola proxy routes — now fixed.
9. Minimum fixes before production?
Auth + rate limit on the Ola routes (done). Then, as scale grows: CAPTCHA on OTP signup and edge rate limiting for checkout.

04 Confidence & caveats

Verified from code: every endpoint's auth posture, rate-limit placement, and per-request downstream call count — read directly from the routes and helpers. High confidence.

Not verified here: provider limit numbers (Ola 100k/mo & ~500/min, Firestore Spark daily quotas, Vercel autoscaling, Razorpay per-account throughput) are documented/general values, not confirmed against live dashboards in this review. Confirm them in your own provider consoles before a campaign.

Idempotency of the payment finalize path is verified by code reading (transaction + webhook dedupe + amount/customer checks), not by an executed emulator test.
