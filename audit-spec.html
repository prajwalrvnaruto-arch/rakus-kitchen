03 Hidden business rules

The non-obvious logic — the rules a new engineer would miss reading the types alone.

The extra-meat cap is a pooled dynamic budget

An extra-meat line has no structural pointer back to any biryani. allowedExtraMeatUnits sums cap × qty across every biryani line of a given meat, so two ½ kg chicken biryanis (cap 1 each) pool to a budget of 2, spendable by a single add-on. The pooled sum is the only source of truth; reconcileExtraMeatLines spends it greedily on every cart change, and the server re-runs the same check at checkout.

Phone normalization is target-partner-driven

The same stored number takes different shapes per consumer: WhatsApp wants international 919606888096; Porter's receiver field and the carrier payloads want the bare 10 digits 9606888096. Both now resolve through one canonical 10-digit form and fail loudly rather than emitting a silently-truncated number.

The server never trusts client prices

recomputeOrderTotals takes only (menuId, variant, qty); any submitted price is ignored. A line that can't be resolved returns a hard error instead of a best-effort charge — a tampered total is caught because price is looked up fresh.

Sentinels and structural safety

A biryani's price: 0 is a sentinel meaning "look it up in the tier table," not "free." Catering items live in a separate array that menuItemById never searches, so a catering id can never resolve a price — checkout rejects it by omission rather than by an explicit guard.

04 Gap analysis

Where the rules bend under sustained, concurrent, Zomato-shaped traffic. Ranked by production risk.

C1Duplicate create-order submissionsCritical

Orders can't double-create, but a double-click fires create-order twice, each spawning a Razorpay order and an inert payment intent — operational clutter at scale.

FixAn in-flight ref makes submit a no-op while an attempt is pending; the visual disabled state was only a partial guard.
C2Silent mid-session repriceCritical

If a price changes while the customer browses, the server reprices at submit and the amount charged differs from the total they confirmed — silently, because the server total wins.

FixThe client sends its displayed total as advisory clientGrandTotal; on mismatch the server returns 409 price_changed and checkout asks the customer to review before paying.
H1Far-future dates acceptedHigh

validateMeal checked advance/holiday/Sunday rules but not that a date fell inside the offered window — a hand-crafted date months out passed.

FixA MAX_ADVANCE_DAYS bound rejects anything past the ordering window.
H2String-coupled price resolutionHigh

Price lookup parsed the display label "1 kg · Chicken". A label refactor or a stray glyph would silently break biryani checkout for every order.

FixParsing is centralized in one parseBiryaniWeight helper, tolerant of spacing, the ½ glyph and a plain 0.5 spelling, reused by both call sites.
H3No automated testsHigh

The pooled-cap math, phone normalizers, date gating and price recompute — exactly where a regression means wrong charges — had no regression net.

FixA Vitest suite covers all four areas (cap pooling, recompute error paths, date boundaries, phone formats). Written; pending a working local install to run.
M1Phone normalizers corrupt silentlyMedium

Short input echoed back a broken wa.me link; an 11-digit string lost its leading digit via slice(-10).

FixA shared normalizeIndianMobile validates against the 6–9 leading-digit rule and returns null for anything invalid; all four consumers (WhatsApp, Porter, Borzo, Shadowfax) route through it.
M2Extrapolated bulk pricingMedium

2 kg / 3 kg biryani prices are extrapolated, not confirmed against a physical card. A data question, not a code bug.

FixA TODO(business) marker flags the rows for confirmation; no logic change.
M3No order-creation rate limitMedium

Genuine, but infra-dependent — needs a shared store (Firestore counter, Upstash). Out of code scope.

StatusDeferred by decision; client guard + existing idempotency hold the line meanwhile.
